# Stable 1.0 launch — Specification

**Status:** Proposed for execution  
**Scope:** Multi-release promotion program  
**Depends on:** `.specs/features/product-completeness-v1/`

## Track A — Premium product requirements

- **REQ-SL-PROD-001:** WHEN stable promotion is proposed, THEN all P0 and P1 requirements in `product-completeness-v1` SHALL be complete or explicitly removed from the supported 1.0 contract before release.
- **REQ-SL-PROD-002:** WHEN a developer opens an ADVPL/TLPP workspace, THEN the product SHALL reach a verified offline changed-files result through native VS Code UI in five minutes or less.
- **REQ-SL-PROD-003:** WHEN a finding is shown locally or in CI, THEN its scope, rule, evidence, confidence, provenance, suggested next action and stable fingerprint SHALL be consistent across VS Code, CLI, MCP and SARIF.
- **REQ-SL-PROD-004:** WHEN model/agent integrations are absent, denied or unavailable, THEN deterministic review, CodeGraph, memory, doctor and evidence workflows SHALL remain usable.
- **REQ-SL-PROD-005:** WHEN TDS is installed, THEN Protheus Engineering Agent SHALL coexist without claiming or duplicating compile, debug, RPO or server ownership.
- **REQ-SL-PROD-006:** WHEN a marketing claim is prepared, THEN it SHALL map to technical evidence or representative pilot evidence and SHALL state limitations.

## Track B — Internal QA environment requirements

These requirements govern release testing. They do not add Docker to the product, its standard configuration or its user-facing support contract.

- **REQ-SL-ENV-001:** WHEN CI runs without external services, THEN Tier 0 legal fixtures and contract-tested virtual services SHALL cover success, denial, malformed, unavailable, timeout and cancellation paths with zero unapproved network calls.
- **REQ-SL-ENV-002:** WHEN the official analyzer is enabled, THEN its full image digest, resource policy, input digests, output and exit mapping SHALL be recorded in the operation evidence.
- **REQ-SL-ENV-003:** WHEN the official PostgreSQL development fixture is enabled, THEN it SHALL bind to loopback, use ephemeral credentials, expose a read-only named-query account and be destroyed after the test.
- **REQ-SL-ENV-004:** WHEN an AppServer compatibility claim is proposed, THEN evidence SHALL come from an owner-authorized environment using lawfully obtained, user-owned Portal TOTVS artifacts and SHALL identify the tested AppServer/RPO/TDS matrix. Commercial-license status is recorded but is not a functional pass criterion for the private QA laboratory. A community image SHALL NOT imply official TOTVS certification, production support, redistribution rights or permission to publish proprietary artifacts.
- **REQ-SL-ENV-005:** WHEN any community container is considered, THEN provenance/license, digest, SBOM, vulnerability, secret, signature, privilege, network, readiness and teardown checks SHALL pass before execution.
- **REQ-SL-ENV-006:** WHEN a Docker-backed result is reported, THEN it SHALL identify the tier and SHALL NOT imply production homologation.
- **REQ-SL-ENV-007:** WHEN external services are unavailable, THEN CI SHALL degrade explicitly or skip only a declared non-gating lane; it SHALL NOT report an unexecuted check as passed.
- **REQ-SL-ENV-008:** WHEN the VSIX/runtime is packaged or installed, THEN no Docker daemon, image, Compose file or container runtime SHALL be required for normal product operation.

## Track C — Stable distribution requirements

- **REQ-SL-REL-001:** WHEN `1.0.0` is tagged, THEN the supported public API SHALL define configuration schema, CLI surface, MCP tools, evidence/SARIF schemas, policy behavior, compatibility range and deprecation rules.
- **REQ-SL-REL-002:** WHEN the Marketplace release is published, THEN it SHALL be a regular release with a version distinct from every pre-release package and all manifests/docs SHALL agree on `1.0.0`.
- **REQ-SL-REL-003:** WHEN the VSIX is released, THEN clean install, upgrade from the latest supported preview, uninstall/reinstall and documented rollback SHALL pass against the actual packaged artifact.
- **REQ-SL-REL-004:** WHEN a supported VS Code/TDS/OS/Node environment is declared, THEN that exact matrix SHALL be tested and published; untested combinations SHALL be labeled unsupported or experimental.
- **REQ-SL-REL-005:** WHEN release artifacts are produced, THEN source archive, VSIX, SBOM, manifest and evidence SHALL be hash-linked to one exact public commit and generated by a protected release workflow.
- **REQ-SL-REL-006:** WHEN a consumer verifies the release, THEN public provenance attestation and documented verification commands SHALL establish its repository, workflow and commit origin.
- **REQ-SL-REL-007:** WHEN the stable product is used, THEN security reporting, privacy, permissions, data handling, support, migration, rollback and deprecation documentation SHALL be public and actionable.
- **REQ-SL-REL-008:** WHEN stable promotion is evaluated, THEN no unresolved blocker/high security, code-review, accessibility or data-loss issue SHALL remain.
- **REQ-SL-REL-009:** WHEN publication is ready, THEN GitHub visibility, immutable release, Marketplace publication and any external announcement SHALL require named owner authorization.

## Human and external validation requirements

- **REQ-SL-UAT-001:** WHEN onboarding is tested, THEN at least three clean-profile participants SHALL complete the core offline workflow without maintainer intervention, with time and failure evidence recorded.
- **REQ-SL-UAT-002:** WHEN accessibility is tested, THEN keyboard-only, focus order, screen reader labels, high contrast and 200% zoom SHALL pass the supported VS Code matrix.
- **REQ-SL-UAT-003:** WHEN effectiveness is claimed, THEN a preregistered representative pilot SHALL compare baseline TDS/VS Code against the product using task time, confirmed findings, first-pass validation, rework and confidence calibration.
- **REQ-SL-UAT-004:** WHEN support readiness is reviewed, THEN issue templates, support policy, security response owner, response targets and a first patch/rollback drill SHALL exist.

## Non-goals

- No full Protheus production container maintained or redistributed by this repository.
- No Docker prerequisite, Docker configuration journey or community image recommendation in the product surface.
- No Electron IDE, terminal, Explorer, Git client, generic chat or generic model marketplace.
- No replacement for TDS compile/debug/RPO administration.
- No requirement for Hermes, Copilot or any one hosted model.
- No stable claim based solely on fixture coverage, mutation score, stars, installs or a version-number change.
